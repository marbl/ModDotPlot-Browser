# moddotplot-rs design reference

> **Authorship note:** This document was generated by ChatGPT 5.6 Sol. The software
> was written by ChatGPT 5.6 Sol under the guidance of Adam Phillippy.

This document is the authoritative implementation guide for moddotplot-rs v0.1. It
records the scientific model, runtime architecture, invariants, important parameter
choices, and extension points. Read it together with the narrower
[scientific specification](SCIENTIFIC_SPEC.md) and the decision records in
[`docs/adr`](adr/).

## 1. Scope and status

moddotplot-rs is an install-free, browser-native comparative genomic dotplot. A user
loads one or more FASTA records, selects any record for each axis, and explores a
containment-derived ANI matrix. All sequence processing and rendering occur in the
browser. A self-dotplot is the ordinary case where the same record is selected on
both axes.

The v0.1 implementation is an initial preview. It is functional and extensively unit
tested, but it is not yet described as research-validated. In particular, the current
contiguous sequence representation has not been approved for the advertised 1 Gb
record limit, and the revised progressive backend needs a current CHM13 benchmark and
broader statistical validation. See [STATUS.md](STATUS.md).

### 1.1 Primary requirements

1. Correct, deterministic scientific output is the first priority.
2. The first useful view appears quickly and may be refined asynchronously.
3. Navigation remains responsive and stale work is abandoned.
4. Plotting, including sequence parsing, is entirely client-side.
5. A record can be compared with itself or with any other loaded record.
6. Similarity and relative strand are independent views of the same calculation.
7. Zoom is tiled, cached, and progressively refined.
8. The terminal zoom is an exact canonical k-mer dotplot.
9. Numeric tiles remain independent of rendering so export can be added later.

### 1.2 Deliberate non-goals for v0.1

* Mobile-browser support
* Persistence or session recovery
* Numeric matrix or image export
* Server-side sequence processing
* Whole-genome concatenation or multi-panel genome plots
* A zero-failure window guarantee for the approximate sketch

## 2. System architecture

```text
FASTA / FASTA.gz / BED / GFF / GTF
                 |
                 v
       TypeScript main thread
       controls, axes, input
                 |
          structured messages
                 |
                 v
       Dedicated Web Worker
       scheduling, cancellation
                 |
           narrow Wasm API
                 |
                 v
        Rust scientific core
  packed DNA -> hashes -> sketches
       -> containment/ANI tiles
                 |
          transferable arrays
                 |
                 v
       WebGL2 tile renderer
  CPU/GPU LRU cache, pan and zoom
```

The Rust core has no third-party dependencies. The Wasm crate only adapts core data
to JavaScript. TypeScript owns files, scheduling, presentation acknowledgements, UI
state, feature tracks, and renderer coordination. WebGL2 owns coloring, not scientific
calculation.

The production bundle contains no CDN resources, analytics, runtime downloads, or
application API requests. It can be hosted as static files over HTTP or HTTPS.

## 4. Data and coordinate model

### 4.1 Sequences

`PackedSequence` stores two bits per base plus one validity bit per coordinate. The
validity bitmap distinguishes A/C/G/T from ambiguous input. Ambiguous bases preserve
sequence coordinates and invalidate every overlapping k-mer; they are never silently
deleted or coerced to a nucleotide.

FASTA is parsed incrementally across arbitrary byte-chunk boundaries. Multiple files
and multiple records are supported. The parser enforces a hard per-record limit of
1,000,000,000 bases. Gzip input is decompressed through the browser's streaming
decompression facility before bytes are passed to Wasm.

### 4.2 Coordinates

Scientific code uses zero-based, half-open intervals `[start, end)`. The browser shows
human-facing coordinates as one-based inclusive intervals. BED input is zero-based
half-open. GFF3 and GTF input are one-based inclusive and are converted at parse time.

The plot uses a square domain whose side length is `max(x_length, y_length)`. Areas
beyond a shorter sequence are marked missing rather than rescaled. This preserves the
same coordinate scale on both axes and a geometrically meaningful self-diagonal.

### 4.3 Numeric tile contract

A tile contains equally sized row-major arrays:

| Array | Type | Meaning |
| --- | --- | --- |
| `identity` | `u16` | `round(ANI * 10,000)`; `65,535` is missing |
| `direction` | `i16` | Signed strand evidence, scaled for transport |
| `direction_support` | `u16` | Number of informative strand votes |
| `x_bases` | optional `u8` | Exact-mode x-axis base code used by the similarity palette |

This contract is the future export boundary. Export code should consume numeric tiles,
not read pixels back from WebGL.

## 5. Scientific pipeline

### 5.1 Canonical k-mers and hashing

The default k-mer length is 21. Each valid k-mer and its reverse complement are
compared; the lexicographically smaller packed form is canonical. Its orientation is
recorded as forward or reverse. Palindromic or otherwise uninformative orientation is
handled without inventing a directional vote.

The production path uses ntHash2 with its published constants and rolling recurrence.
Hashes are generated as a stream for the requested range and are not stored for every
k-mer in a chromosome. The default fixed seed is 42, providing deterministic output
across supported browsers.

MashMap-compatible MurmurHash3 and packed `fmix64` implementations remain in the core
for fixtures, comparisons, and benchmark reproducibility. They are not the production
hash path.

### 5.2 Axis partitioning

At matrix resolution `R`, an axis is divided into `R` core cells over the shared square
domain. Hashes are assigned in one pass to `2R` half-cells. A core is a pair of adjacent
half-cells. Its expanded interval includes an additional half-cell on each side where
available.

This construction implements the ModDotPlot out-of-register correction without
rescanning each overlapping window. Every plotted cell compares one core interval
with one expanded interval in each direction.

### 5.3 Production sketch: one-permutation b-bit signatures

For each axis interval, one-permutation hashing (OPH) maps a 64-bit hash into one of a
power-of-two number of registers. Each register retains the smallest full 64-bit
winner and its canonical orientation. A HyperLogLog sketch with precision 12 estimates
the distinct cardinality of the interval.

At finalization, winners are represented as a bit-sliced signature. Similarity uses
the low 14 fingerprint bits. A wider verification fingerprint prevents low-bit
collisions from creating false strand votes. Bit-slicing compares many registers with
word operations and avoids a merge-sort per matrix cell.

The advanced controls expose:

* Quick registers: 128, 256, 512, or 1,024; default 256
* Detailed registers: 512, 1,024, 2,048, or 4,096; default 2,048

The UI constrains quick registers to be no greater than detailed registers. Register
count is the direct accuracy/cost control: more registers increase the expected number
of comparable winners and reduce sampling variance, while increasing construction,
comparison, and memory cost. It is not a fixed k-mer sampling fraction because bucket
occupancy depends on interval cardinality and sequence composition.

### 5.4 Similarity, containment, and displayed ANI

Let `m` be the number of comparable registers and `e` the number whose b-bit
fingerprints agree. The observed agreement is corrected for the random collision rate
`2^-b` to estimate Jaccard similarity `J`. With cardinality estimates `|X|` and `|Y|`,
the intersection estimate is

```text
I = J (|X| + |Y|) / (1 + J)
```

and directed containment is

```text
C(X, Y) = I / |X|.
```

The plotted ModDotPlot score is the larger of the two out-of-register comparisons:

```text
Cplot = max(C(Xcore, Yexpanded), C(Ycore, Xexpanded)).
```

The value displayed and colored as identity is

```text
ANI = Cplot^(1/k).
```

This is a containment-derived ANI estimate, not a Jaccard-derived MashMap ANI. The
exact all-k-mer containment implementation is the scientific oracle. MashMap's
bottom-s estimator is retained as a useful independent sanity check, not as ground
truth.

### 5.5 Direction evidence

Every retained OPH winner carries the orientation of its canonical k-mer. When two
verified winners agree, equal orientation contributes a forward vote and unequal
orientation contributes a reverse vote. The tile stores the signed balance and the
number of informative votes separately. Similarity mode ignores the direction fields;
orientation mode maps forward and reverse evidence to distinct colors.

### 5.6 Adaptive sparse correction

OPH is fast, but high-containment comparisons between cardinality-imbalanced intervals
can have low Jaccard and too few common registers. Detailed axis construction therefore
retains an exact, distinct `(hash, orientation)` set for a core only while it remains
at or below 2,048 hashes. If it exceeds the cap, the partial set is discarded so the
memory bound is real.

For a sparse core, the code models the expected number of true OPH matches at the 80%
ANI floor. Assuming a Poisson approximation, the probability of observing at least
one true match is

```text
P(match >= 1) = 1 - exp(-lambda).
```

The 99% target corresponds to `lambda = -ln(0.01)`, approximately 4.605. Exact
directed containment is used only when the modeled OPH probability falls below this
target and an exact sparse core is available. The expanded target hashes are streamed
and deduplicated for that calculation.

This correction is intentionally absent from the quick pass. The policy is a bounded
variance safeguard, not a window guarantee. An occasional approximate miss is accepted,
especially below the practical 80% identity floor.

### 5.7 Why minmers are not the production backend

The repository contains a bounded-memory rolling minmer implementation and independent
bottom-s references. Minmers provide a deterministic window guarantee and were a
serious backend candidate. Benchmarking showed that constructing and merge-comparing
their variable-length sketches was substantially slower for the all-pairs matrix than
fixed-register, bit-sliced OPH.

The product requirement was refined from a mandatory window guarantee to accurate
window-pair estimates with a probabilistic sparse safeguard. The production browser
backend therefore uses ntHash2 plus OPH/b-bit signatures. The minmer implementation
must remain tested as a reference and experimental alternative, but future agents
must not describe it as the current browser sketch.

### 5.8 Exact terminal k-mer mode

When the selected resolution reaches one cell per base coordinate, approximate
sketching stops. `compute_kmer_tile` compares exact canonical k-mer hashes at every
k-mer start. A matching canonical hash is a dot; orientation is derived from the two
canonical orientations. Ambiguous or incomplete k-mers are missing.

In similarity mode, exact matches are colored by the x-axis nucleotide using the
standard genome-browser palette: A green, C blue, G orange, and T red. Nonmatches and
missing positions are white. Orientation mode remains forward/reverse colored.

`base.rs` contains an earlier exact single-base comparison kernel for reference and
tests. It is not the production terminal mode and should not be substituted for the
k-mer kernel.

## 6. Progressive computation

Every new sketch level follows this state machine:

1. The main thread increments a viewport generation and sends the visible tiles plus
   a one-tile halo to the worker.
2. Wasm builds the requested axis level with the quick register count.
3. The worker computes all visible quick tiles before background halo work.
4. The worker emits `preview-complete` only after all required quick tiles were sent.
5. The main thread asks the renderer to present a frame and waits for
   `requestAnimationFrame`.
6. The main thread replies `preview-presented`.
7. Only then does the worker construct the detailed level and replace current tiles.
8. If pan, zoom, reset, axis selection, or parameters change, a new generation
   invalidates the old queue. Work is preempted between tile jobs.

This ordering is deliberate: quick and detailed construction do not contend for CPU
before the first useful viewport has actually appeared.

Self-comparisons compute one triangle and transpose tile data across the diagonal.
This optimization is allowed only where the numeric result is symmetric under the
transpose operation.

## 7. Tiling, zoom, and visual continuity

The selected plot-detail preset defines the full-view matrix: 500, 1,000, 2,000, or
4,000 cells per axis. The default is a genuine 1,000 by 1,000 matrix; CSS canvas size
does not change the scientific resolution.

As the user zooms, resolution advances by powers of two relative to the overview and
is capped by the shared domain length. Visible work is divided into 256 by 256 tiles.
A one-tile halo is requested after visible tiles to reduce blank edges during the next
small pan.

The renderer keeps cached coarser levels underneath the active layer. Zoom immediately
applies the viewport transform to this lower-resolution image, then overlays quick and
detailed tiles as they arrive. Reset immediately selects the base overview, avoiding a
stale high-resolution composite.

Tile identity includes sequence selections, scientific parameters, resolution, tile
coordinate, and quality tier. A tile is immutable under its key; results from another
generation or parameter set cannot contaminate the current view.

## 8. Caching and memory behavior

### 8.1 Wasm axis cache

Zoom-level axis summaries use a true least-recently-used cache with a nominal 192 MiB
byte budget. Keys include the sequence, range, resolution, register count, and sparse
policy. Only the selected quick and detailed prepared levels are retained for a
generation.

### 8.2 Renderer tile cache

The renderer uses a nominal 192 MiB combined CPU/GPU tile budget. The overview is
pinned. Currently visible tiles and the nearest coarse fallback are protected from
eviction, so a large protected working set can temporarily exceed the nominal budget.
Eviction is coordinated with the worker so its published-key set does not claim a tile
that the renderer has removed.

### 8.3 Reported memory

The status line shows an estimate composed of packed sequence data, Wasm structures,
numeric tile arrays, and estimated GPU textures. Browser and driver overhead cannot be
measured precisely. WebAssembly linear memory is a high-water allocation: pages are
normally reused by the allocator but are not returned to the operating system during
the session. This distinction explains why operating-system memory may not fall as far
as the application's live-object estimate after eviction.

`Clear` drops loaded records, prepared levels, tiles, annotations, and UI state. A page
reload also recreates the Wasm instance and releases its linear memory.

## 9. Rendering and color transfer

The WebGL2 renderer uploads identity as `R16UI`, direction as `R16I`, support as
`R16UI`, and optional exact-mode base codes as `R8UI`. Shader uniforms apply the color
transfer function at draw time, so moving the heatmap controls does not recompute tiles.

Similarity mode has three user-set identity anchors constrained to 80% through 100%.
Values below the minimum are white, values above the maximum are black, and values
within the interval follow the established yellow-red-dark ModDotPlot gradient with
the middle handle controlling its inflection. The compact histogram is computed from
the refined overview in the same 80% to 100% range.

Orientation mode uses separate forward and reverse colors and modulates confidence
from direction support. Sparse or absent direction evidence should never be interpreted
as a confident strand call.

Axes choose conventional rounded tick positions. Hover reports only identity and the
two coordinate intervals. At exact zoom, nucleotide color is carried by matching plot
pixels instead of a separate sequence track.

## 10. Feature tracks

BED3 through BED12, GFF3, and GTF are accepted. Files can be dropped on an axis or
chosen by double-clicking it. A track is attached only after at least one record name
matches the selected FASTA header, using either the full header or its first
whitespace-delimited token. A file with no matching sequence name is rejected. Parsed
intervals are also checked against sequence bounds.

BED blocks and GFF/GTF exon or CDS children are rendered as conventional box-and-stick
models. GFF grouping prefers `Parent`, then transcript, gene, or feature identifiers.
To preserve interaction speed, at most 500 visible feature models are drawn for one
axis view. This is a rendering cap, not a change to the loaded sequence.

`ComputeSession` is the sole mutable Wasm entry point.

| `sequences` | Return metadata for all loaded records |
| `estimated_memory_bytes` | Estimate live Wasm-owned data and cache bytes |

| `begin_prepare_preview` | Start a quick level without sparse exact sets |
| `begin_prepare_comparison_with_hash` | Selectable-hash benchmark/reference preparation |

| `cancel_preparation` | Abandon the active preparer safely |

## 14. Worker protocol and cancellation

Main-to-worker messages cover load chunks, finish load, prepare comparison, cancel,
preview paint acknowledgement, request tiles, evict tile keys, and clear. Worker-to-main
messages cover readiness, status/progress, sequence metadata, comparison readiness,
preview completion, tiles, final completion, memory estimates, and errors.

Every computation request carries a monotonically increasing generation or request ID.
The main thread ignores stale output. The worker checks cancellation between bounded
axis-construction chunks and tile jobs. JavaScript cannot interrupt a Wasm function in
the middle of one tile, so tile size and chunk size are also latency controls.

## 15. Correctness, tests, and reproducibility

The current validation stack contains:

* Rust unit and integration tests for packed DNA, FASTA streaming, hashing, minmers,
  OPH, HLL, containment, sparse correction, range summaries, and exact k-mer tiles
* Differential scalar/bit-sliced/inverted matrix tests
* Statistical tests against exact k-mer sets and MashMap bottom-s distributions
* TypeScript tests for axes, features, heatmap, viewport, detail selection, tiles, and
  worker protocol behavior
* A Phase 0 synthetic and CHM13 benchmark harness with frozen TSV and Markdown reports
* CI formatting, strict Clippy, all Rust tests, Wasm target check, TypeScript tests,
  Wasm build, typecheck, and production bundle build

The statistical fixture currently requires mean ANI error below 0.015 and p95 below
0.035 against exact sets. The independent MashMap comparison allows mean below 0.02
and p95 below 0.04. These are engineering gates, not yet a complete scientific
validation claim.

Any change to hashing, sketch construction, containment, sparse policy, matrix
boundaries, missing values, or orientation must update tests, this document, the
scientific specification, and an ADR when it changes a durable decision.

## 16. Extension points

### 16.1 Export

Add export above the numeric tile interface. A future export request should explicitly
name the sequence IDs, coordinates, k, resolution, quality/register tier, scoring mode,
and color settings. Scientific exports should default to a completed detailed tier or
allow a custom register count.

### 16.2 Persistence

IndexedDB or Origin Private File System storage could preserve packed sequences,
annotations, and costly prepared levels. Persistence must be opt-in, versioned by
scientific parameters and data format, and clearly expose deletion. OPFS is also the
planned spill layer for sharded very large sequences.

### 16.3 One-gigabase records

The parser already enforces the intended 1 Gb ceiling, but the current contiguous Wasm
representation is not sufficient evidence of practical support. Before making that
claim, implement packed-sequence and sketch sharding, transient OPFS spill, controlled
allocation-failure behavior, and measured peak CPU/GPU/browser memory tests.

### 16.4 Additional annotations

The axis overlay is intentionally separate from numeric tiles. New formats should
normalize into `FeatureTrack`, preserve source coordinates and attributes, validate
record identity, and remain bounded at render time.
