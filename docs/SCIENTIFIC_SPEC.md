## Coordinates and input

Core APIs use zero-based, half-open `u64` coordinates. The UI converts them to
one-based inclusive labels. A/C/G/T are valid case-insensitively; every other input
symbol preserves its coordinate but invalidates overlapping k-mers. A missing axis
suffix or an interval without valid k-mers uses the `65535` identity sentinel rather
than zero similarity.

Each selected axis pair uses the longer record length as a square common domain. A
shorter record therefore has an explicit missing suffix and does not distort the
diagonal angle.

## Hashing and reference minmers

The selected register backend uses the official ntHash2 canonical split-rotation
rolling hash. Vectors are pinned to ntHash source commit
`c26bd4572a19de81e30d55042dbd33c1fd21d4b6`. The independent MashMap reference hashes
ASCII forward and reverse-complement k-mers using the first 64 bits of
`MurmurHash3_x64_128`, seed 42, and selects the lower hash. Its fixtures are pinned to
MashMap implementation commit `1a07d0e`.

The rolling minmer reference retains the lowest `s` distinct hashes in every window
of `w` consecutive k-mer starts. It emits half-open intervals of window starts for
which a hash remains selected and splits every interval to length at most `w`. Hash
duplicates combine orientation as forward, reverse, or both. No chromosome-wide k-mer
hash array is built.

## Sketch heatmap score

Each axis cell has a core sketch and a sketch expanded by half a cell on each side.
For core cells `A` and `B`, the heatmap uses:

```text
C_A = containment(A, B+)
C_B = containment(B, A+)
C   = max(C_A, C_B)
ANI = C^(1/k)
```

The optimized backend estimates Jaccard from aligned b-bit one-permutation registers,
estimates cardinality with HLL, and converts Jaccard to intersection and directed
containment. Matrix values are `round(ANI * 10000)` in `u16`. Full or wider winner
fingerprints, not b-bit collisions, supply direction votes. Because the ANI `1/k`
transform can amplify one chance b-bit collision into a visually strong false match,
the b-bit estimate is zero unless the 32-bit verification channel contains at least
one matching winner. A tied directed score combines evidence from both directions.

The default detailed tier uses 2,048 registers, 14 comparison bits, a 32-bit verification
fingerprint, and HLL precision 12. A visibly provisional 256-register pass is drawn
first at every sketch level. Direct OPH can undersample a high-containment
comparison when a low-cardinality core is compared with a much larger expanded set.
For detailed tiles, the backend therefore evaluates the expected number of aligned
winners at `ANI = 0.80`. If `1 - exp(-expected_matches) < 0.99` and the complete core
contains at most 2,048 distinct canonical hashes, that directed containment and its
orientation evidence are computed exactly. The threshold is approximately 4.605
expected matches. Complete sparse-core hashes are retained during the ntHash2 stream
and the partial set is released immediately if it exceeds the cap.

The exact sparse channel is not a second sketch. It uses every distinct canonical
hash in the eligible core and deduplicates matching target cells before computing
containment. A core above the cap remains on OPH. This probability controls complete
match detection at the chosen floor; it is not a guarantee of precise containment
from a single register.

The scientific bottom-s reference instead merges two sorted sketches, takes the
lowest `s` distinct hashes of their union, and estimates directed containment as the
sampled shared-x count divided by the sampled x count. This comparison is exact when
the union contains at most `s` hashes.

Forward votes require matching unambiguous canonical orientations. Opposite
orientations vote reverse. A hash observed in both orientations is ambiguous and does
not vote either way. Direction is stored as `(forward - reverse) / (forward + reverse)`.

## Exact k-mer mode

The heatmap estimator stops at the finest sketch level that remains meaningful. At
one matrix interval per k-mer start, tiles are exact: equal canonical k-mers are
matches, unequal valid k-mers are mismatches, and ambiguity-overlapping or padded
k-mers are missing. Matching canonical k-mers with equal source orientation are
forward; opposite source orientations are reverse. The UI labels this mode as exact.

## Change control

Hash algorithms, seeds, ambiguity behavior, interval assignment, containment
transforms, direction rules, fixed-point encoding, and accepted statistical error are
versioned scientific behavior. An optimization may change them only with an explicit
specification update, independent reference tests, and measured acceptance evidence.
